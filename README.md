# knowledgebase-askgov

A retrieval pipeline (RAG) for Guyana government process documents that runs on your own machine:

```
upload ─► load (pdf/docx/html/md/txt/csv/json, OCR for scanned PDF pages, PDF tables and headings)
       ─► structure-aware chunking (headings, recursive inside long sections) ─► LLM topic tags per section
       ─► OpenAI embeddings via LiteLLM ─► pgvector (Docker, local)
       ─► (async) kb graph worker: LLM entity/relation extraction per document ─► Neo4j

query  ─► LLM router (normal, multi_intent, comparison, multi_hop, conditional, list, process)
       ─► per search: embed ─► pgvector HNSW + keyword full-text + knowledge graph (fused by RRF)
       ─► JSONB metadata filters on all three ─► Cohere rerank ─► relevance cut (rerank ≥ 0.5 and cosine ≥ 0.245)
       ─► top-k chunks with citations, graph facts, drift warnings + a numbered `context` block
       ─► optional answer generation (`kb ask`, MCP `ask`) that cites the context
```

Answers are generated by [src/kb/generation.py](src/kb/generation.py) (`KB_GENERATION_MODEL`, default `gpt-4o-mini`); `kb query` and `POST /query` return retrieval results only. The pipeline is also available as a LangChain retriever with a ready-made RAG chain.

## Setup (Windows / PowerShell)

```powershell
docker compose up -d                 # pgvector/pgvector:pg17 on localhost:5433 (5433 avoids a local Postgres on 5432)
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -e ".[dev]"
copy .env.example .env               # then set OPENAI_API_KEY and COHERE_API_KEY
kb init                              # creates extension, tables, HNSW + GIN indexes (runs all migrations)
```

### Database migrations (Alembic)

The schema is managed by Alembic migrations in [src/kb/db/migrations/versions/](src/kb/db/migrations/versions/). Each `KB_DB_SCHEMA` keeps its own `alembic_version` table, so several knowledge bases can share a database. The API and CLI only *check* that the schema is current at startup and never change it; apply migrations as a deploy step:

```powershell
kb migrate --status                  # current vs latest revision
kb migrate                           # upgrade to latest (same as kb init)
kb migrate -1                        # roll back one revision
alembic revision -m "add review_by"  # new migration file; write the SQL in upgrade()/downgrade()
```

Revision `0001` is a baseline written with `IF NOT EXISTS`, so a database created before Alembic was added is adopted by `kb migrate` without changes.

If `COHERE_API_KEY` is empty, results come back in vector-similarity order and `reranked` is `false`.

## Metadata and filters

Every chunk stores a JSONB `metadata` object. It combines three sources:
- the metadata you supply at upload
- metadata found in the file itself, such as a PDF or DOCX title or an HTML `<title>`
- reserved keys the pipeline sets: `document_id`, `filename`, `file_type`, `chunk_index`, `page`, `char_start`, `char_end`, `uploaded_at`

You can't set the reserved keys yourself. You can filter on any key:

```jsonc
{"department": "health"}                          // equality (GIN-indexed containment)
{"year": {"$gte": 2020, "$lt": 2025}}             // numbers, or ISO date strings
{"file_type": {"$in": ["pdf", "docx"]}}
{"tags": {"$contains": "covid"}}                  // array membership
{"author": {"$exists": true}}
{"source.agency": "CDC"}                          // dotted path into nested objects
{"$or": [{"department": "health"}, {"$not": {"draft": true}}]}
```

The supported operators are `$eq $ne $in $nin $contains $gt $gte $lt $lte $exists $and $or $not`. Keys are validated and passed as bind parameters.

Filtered searches set `hnsw.iterative_scan = relaxed_order` (pgvector ≥ 0.8) and raise `hnsw.ef_search` to the number of candidates. This way, a selective filter still returns a full candidate set.

## Hybrid search and relevance

Each query runs two searches, both restricted by your metadata filters:
- **Vector search** (pgvector HNSW) finds chunks with similar meaning.
- **Keyword search** (PostgreSQL full-text search on the generated `chunks.content_tsv` column, GIN-indexed) finds chunks that share exact words: phone numbers, fees, form names, acronyms.

**Merging:** the two lists are combined by Reciprocal Rank Fusion, `score = Σ 1/(60 + rank)`, so a chunk found by both methods ranks first.

**Ranking and the relevance cut:** Cohere reranks the merged list. Results scoring below `KB_MIN_RERANK_SCORE` (default 0.5) are dropped, and so are results whose cosine similarity is below `KB_MIN_VECTOR_SCORE` (default 0.245): Cohere gives contentless queries such as "hii" high scores against short generic chunks, and the vector floor catches those. If nothing passes, the response has `status: "no_relevant_context"` and empty `results`.

**Response fields:** each result reports `found_by` (`vector`, `keyword` or `both`) and a `keyword_score`.

**Turning hybrid off:** send `"hybrid": false` in the request, or use `kb query ... --no-hybrid`.

**Keyword matching details:**
- A chunk matches if it contains *any* of the question's words after stemming and stopword removal. `ts_rank_cd` favours chunks that match more of the words, close together.
- The ranking is close to BM25, but not exact: it has no IDF weighting.
- For true BM25, switch the database image to ParadeDB (`pg_search`). The Cohere rerank step makes this unnecessary at small scale.

**When hybrid changes results:** with fewer chunks than `candidate_k` (default 40), vector search already passes every chunk to the reranker. Hybrid starts adding recall once the knowledge base is larger than that.

**If Cohere fails or is rate-limited:** results fall back to fused order and the response includes a `warnings` entry. The cut then compares cosine similarity against `KB_MIN_VECTOR_SCORE`, which is less reliable.

## LangChain

LangChain is used for two things:

- **Chunking:** `langchain-text-splitters`' `RecursiveCharacterTextSplitter`, using its Markdown heading separators plus sentence boundaries. Character offsets for citations are computed in [src/kb/ingestion/chunking.py](src/kb/ingestion/chunking.py) instead of with LangChain's `add_start_index`. That option subtracts the overlap in tokens from a length in characters, so it can return `-1` when chunks are measured in tokens.
- **Composability:** [src/kb/retrieval/langchain_retriever.py](src/kb/retrieval/langchain_retriever.py) wraps the pipeline as a `BaseRetriever`. Each result becomes a `Document` whose metadata holds the chunk's metadata, its scores and a `citation`.

```python
from kb.deps import get_lc_retriever
from kb.generation import build_rag_chain

retriever = get_lc_retriever(top_k=3)
docs = retriever.invoke("flu clinic hours", filters={"department": "health"})

# Later, with any LangChain chat model (e.g. ChatLiteLLM from langchain-litellm):
chain = build_rag_chain(retriever, llm)
chain.invoke("when are flu clinics open?")   # {"question", "sources": [Document], "answer": "... [1]"}
```

Some parts intentionally stay outside LangChain:
- **Storage and search** use the project's own pgvector code instead of `langchain-postgres`. That keeps the schema, the HNSW `ef_search` and `iterative_scan` tuning for filtered searches, the GIN-indexed filters and exact page and character citations.
- **Embeddings** go directly through LiteLLM.
- **Reranking** calls the Cohere SDK directly.

Swapping in LangChain wrappers for these would add dependencies without adding capability.

All settings are in `.env`; see [.env.example](.env.example). The ones you'll most likely change:

|---|---|---|

| `KB_EMBEDDING_SEND_DIMENSIONS` | `true` | Ask the API for `KB_EMBEDDING_DIM` dimensions (3-large returns 3072 otherwise) |
| `KB_EMBEDDING_DIM` | `1536` | Must match the model. The table is created with this size. |
| `KB_EMBEDDING_API_BASE` | — | Point at a LiteLLM proxy or Azure endpoint |

| `KB_STRUCTURE_MIN_HEADINGS` | `3` | Documents with fewer headings are chunked recursively |
| `KB_TABLE_EXTRACTION` | `true` | With `structure`: rebuild PDF/DOCX/HTML tables as markdown tables, split only between rows |

| `KB_TOPIC_TAGGING` | `true` | At ingest, an LLM (`KB_TOPIC_MODEL`, default `gpt-4.1-mini`) gives each section up to `KB_TOPIC_MAX_PER_SECTION` (3) topic names, stored as `topics` on its chunks; `false` skips the call |
| `KB_OCR_MODE` | `auto` | `auto` OCRs only PDF pages without a text layer, `force` OCRs every page, `off` disables OCR |
| `KB_OCR_ENGINE` | `rapidocr` | `rapidocr` (pip only) or `tesseract` (needs the Tesseract binary and `pip install -e ".[tesseract]"`) |
| `KB_OCR_DPI` | `300` | Render resolution for OCR; lower is faster, higher helps with small or faint print |
| `KB_MAX_DOCUMENT_AGE_DAYS` | `365` | A document with no `review_by` date counts as stale after this many days; `0` disables |
| `KB_SOURCE_TIMEOUT_S` | `30` | `kb refresh`: download timeout for source URLs |

If you change the embedding model or dimension later, re-ingest into a fresh database. `kb init` refuses to start when the dimension doesn't match the existing table.

## Behaviour notes

- **Dedup:** a file whose bytes match an existing document returns `status: "duplicate"`.
- **Versions:** every document has a `doc_key` (default: the filename; set `--doc-key` / form field `doc_key` when the filename changes between editions, e.g. `Booklet_V2.pdf` → `Booklet_V3.pdf`). Uploading changed content under an existing `doc_key` adds version N+1 and supersedes the previous one; only the current version is searchable. `valid_from` / `valid_until` (YYYY-MM-DD) also keep a version out of search before or after those dates, and `review_by` records when the content should be checked again. `replace=true` deletes earlier versions instead of keeping them. Deleting the current version makes the previous one current again. `kb list --all` and `GET /documents?include_history=true` show superseded versions; `GET /documents/{id}/versions` lists one document's history.
- **Knowledge drift:** see the next section.
- **Topics** ([src/kb/ingestion/topics.py](src/kb/ingestion/topics.py)): consecutive chunks with the same heading path (or page) form a section; an LLM names each section's subjects, reusing topics already in the knowledge base so the same subject gets the same name across documents. Filter on them with `{"topics": {"$contains": "Leave management"}}`. If the call fails, the document is stored without topics and a warning is logged.
- **PDF pages:** with `KB_CHUNK_STRATEGY=recursive` each page is chunked on its own. With `structure` a section can run across a page break; the chunk's `page` is where it starts and `metadata.page_end` where it ends.
- **Scanned PDFs (OCR):** a page whose text layer has fewer than `KB_OCR_MIN_CHARS` (20) letters or digits is rendered at `KB_OCR_DPI` and read with OCR, so scanned, mixed and photographed PDFs ingest normally. Chunks from those pages carry `"ocr": true` in their metadata, which you can filter on. RapidOCR runs on the CPU at roughly 3–6 seconds per page; the first OCR call loads the models (about 1 second). Text-layer PDFs are not affected. Use `KB_OCR_MODE=force` for PDFs whose text layer is garbled.
- **Structure-aware chunking** (`KB_CHUNK_STRATEGY=structure`, the default; [src/kb/ingestion/structure.py](src/kb/ingestion/structure.py)):
  1. *Headings.* Markdown, HTML and DOCX headings become `#` markers. In PDFs, headings are found from the fonts ([src/kb/ingestion/pdf_headings.py](src/kb/ingestion/pdf_headings.py)): short lines larger than the body text or bold at body size. Levels come from chapters (`Chapter 4:`), numbering (`4.1` under `4.`), questions (`...?` under their category) and font size. Contents pages, bullets, wrapped sentences, page numbers and running headers are left out. The text itself still comes from pypdf, so `contains` phrases in eval files keep matching.
  2. *Sections* run from a heading to the next one, across pages, and know their heading path.
  3. *Fitting:* a section that fits in `KB_CHUNK_SIZE` is one chunk; a longer one is split recursively (paragraph > line > sentence > word, with overlap) inside the section only; sections below `KB_CHUNK_MIN_TOKENS` are merged with their siblings under the same parent heading, never across a higher heading.
  4. *Tables:* PDF tables are located with pdfplumber (ruling lines) and rebuilt from word positions as markdown tables ([src/kb/ingestion/pdf_tables.py](src/kb/ingestion/pdf_tables.py)): columns from the header cells, rows starting at each step number, wrapped lines joined to their row, a table continuing from the previous page given that table's header. Single-column boxes, flowchart nodes and nested boxes are ignored. DOCX and HTML tables become markdown tables too. A table is never split inside a row: one that fits stays in one chunk, a larger one is split between rows with its title and header repeated, so every row arrives with its column names. A process title row inside a table ("| 2. | Firearms Registration | |") becomes a section heading and splits the table there. Chunks holding a table get `has_table: true`. Set `KB_TABLE_EXTRACTION=false` to turn this off.
  5. *Context:* every chunk starts with its heading path, e.g. `[Chapter 4: GENERAL REGISTRAR OFFICE > Agency Processes for Digitization > 1. Births and Deaths Certification Process]`, which the embedding, the keyword index and the LLM all see.
  6. *Metadata* on each chunk: `section_path`, `heading`, `page_end`, `chunk_strategy`, `service` (the numbered process it belongs to, e.g. `Chapter 1: MINISTRY OF HOME AFFAIRS > TINT Waiver Application`, the same for that process's current-state and desired-state pages, so they can be fetched together with `{"service": "..."}`).

  Documents with fewer than `KB_STRUCTURE_MIN_HEADINGS` headings fall back to recursive chunking. `kb chunks <file>` shows the result without a database. Changing the strategy needs a re-ingest: `kb ingest <files> --replace` (identical bytes are otherwise skipped as duplicates), then regenerate chunk-id eval files with `scripts/expected_to_chunk_ids.py`, because chunk labels follow chunk order.

## Knowledge graph (Neo4j)

An LLM reads each uploaded document as a whole and extracts its entities and relations into Neo4j; deleting data in Postgres removes it from the graph automatically ([src/kb/graph/](src/kb/graph/)):

```
kb ingest ─► document text + chunks (Postgres) ──triggers──► graph_outbox ──NOTIFY + poll──► kb graph worker ─► Neo4j
                                                     'extract' (whole document, LLM) · 'delete' · 'document' (version flag)
```

- **Queue.** Triggers on `chunks`, `documents` and `document_texts` write a row to `graph_outbox` in the same transaction, and `NOTIFY kb_graph` wakes the worker: storing a document's full text at upload (`document_texts`, migration `0006`) queues one `extract` row; a chunk delete (including cascades from a deleted document and deletes made by hand in SQL) queues `delete`; a version change queues `document`; a truncate queues `truncate`. Chunk inserts and updates are not queued (migration `0007`), because the graph stores no chunks. Nothing is queued until `kb graph init` turns the graph on for the schema.
- **Document-level extraction** ([document.py](src/kb/graph/document.py)). The worker sends the **whole document** to `KB_GRAPH_EXTRACTION_MODEL` (default `gpt-4.1-mini`, via LiteLLM, temperature 0, JSON output). A document larger than `KB_GRAPH_WINDOW_TOKENS` (20k) is read in parts cut at its chapters (then sections, then paragraphs), each part with the document's outline as context; a reply cut off at `KB_GRAPH_MAX_OUTPUT_TOKENS` halves the part and retries. Each fact is traced back to the chunk that contains its quote (`source_chunk`), and each entity is linked to every chunk that names it.
- **Vocabulary.** The model uses a fixed vocabulary ([schema.py](src/kb/graph/schema.py)): entities Service, Office, Role, Requirement, Fee, Form, Region, Law, Deadline, Contact; relations REQUIRES, COSTS, HANDLED_BY, LOCATED_IN, GOVERNED_BY, HAS_DEADLINE, USES_FORM, PERFORMED_BY, APPROVES, PART_OF, CONTACT_FOR. Every item must quote the chunk; items whose quote isn't in the chunk, whose type isn't in the vocabulary or whose relation runs the wrong way are dropped.
- **Entity resolution.** Names are normalised and mapped through an alias table ("GRO" = "General Register Office"), so one real-world thing is one node; extend it with `KB_GRAPH_ALIASES_FILE`.
- **Graph.** `Document -MENTIONS {chunk_ids, quote}-> Entity`, and facts `Entity -[REQUIRES|COSTS|...]-> Entity` carrying `source_chunk`, `document_id`, `version`, `current` and `quote`. There are no chunk nodes: chunk text and vectors stay in Postgres, and the graph keeps only chunk ids as properties. Each schema has its own namespace (`kb` property), so one Neo4j can hold several knowledge bases.
- **Deletes.** Deleting a chunk removes the facts traced to it and its id from mention lists; deleting a document also removes its `Document` node and remaining facts; entities left unconnected are removed too. A superseded version's document node and facts get `current = false`.
- **Recovery.** If Neo4j or the LLM is down, queue rows wait and are retried with backoff. `kb graph sync` reconciles in full (removes graph chunks Postgres no longer has, queues missing ones, refreshes version flags, purges week-old queue history); run it nightly. `kb graph rebuild` starts over (after changing the prompt, vocabulary or aliases).

```powershell
docker compose --profile graph up -d          # Neo4j 5 community; browser http://localhost:7474 (neo4j / KB_NEO4J_PASSWORD)
kb migrate                                    # adds graph_outbox and the triggers (revision 0005)
kb graph init                                 # constraints, enable queueing, queue existing documents
                                              # (documents ingested before 0006 are re-read from their source file)
kb graph worker                               # keep running (like kb serve); --once drains the queue and exits
kb graph stats                                # queue and node/relationship counts
kb graph show "General Register Office"       # facts with quotes and source chunks
kb graph sync                                 # reconcile (schedule nightly)
```

Settings: `KB_NEO4J_URI`, `KB_NEO4J_USER`, `KB_NEO4J_PASSWORD`, `KB_NEO4J_DATABASE`, `KB_GRAPH_EXTRACTION_MODEL` (default `gpt-4.1-mini`), `KB_GRAPH_WINDOW_TOKENS` (20000), `KB_GRAPH_MAX_OUTPUT_TOKENS` (16000), `KB_GRAPH_CONCURRENCY`, `KB_GRAPH_BATCH_SIZE`, `KB_GRAPH_POLL_SECONDS`, `KB_GRAPH_ALIASES_FILE`, and for search `KB_GRAPH_SEARCH` (default `true`; used whenever `KB_NEO4J_PASSWORD` is set), `KB_GRAPH_WEIGHT` (default `1.0`), `KB_GRAPH_TIMEOUT_S` (default `5`), `KB_GRAPH_HOPS` (default `2`). Install the driver with `pip install -e ".[graph]"`.

### Graph search and reranking

Whenever Neo4j is configured, every query also searches the graph ([src/kb/graph/rank.py](src/kb/graph/rank.py)):

```
question ─► vector search ─┐
         ─► keyword search ─┼─► RRF (graph list × KB_GRAPH_WEIGHT) ─► Cohere rerank ─► thresholds ─► results + facts
         ─► graph search  ─┘
```

1. **Entity linking:** the question's words (stopwords dropped, one typo allowed on long words) are matched against entity names and aliases in a Neo4j full-text index.
2. **Scoring:** a chunk that mentions a matched entity scores 1.0 × the match weight, the source chunk of a fact touching it 0.8, a chunk one fact away 0.4; scores add up over entities. Only current (non-superseded) data counts.
3. **Same filters:** graph chunks are loaded from Postgres with the query's filters, current-version and validity rules, so the graph can't surface a chunk the other searches would exclude.
4. **Fusion and rerank:** the three lists are fused by reciprocal rank fusion, then Cohere reranks the candidates and the relevance thresholds apply as before. Results show `found_by` (e.g. `vector+keyword+graph`) and `graph_score`.
5. **Facts:** graph facts whose source chunk is in the results come back in `facts`, each cited with that chunk's label (`[1]`), and `kb ask` / MCP `ask` give them to the LLM with the passages.
6. **Failure:** if Neo4j is unreachable (connect limit `KB_GRAPH_TIMEOUT_S`, default 5 s), the query continues with vector and keyword search and a warning.

Per request: `"graph": false` turns it off. `kb eval --compare` adds `hybrid+rerank (no graph)` and `hybrid+graph+rerank` rows when graph search is on.

### Question types (query router)

Before searching, an LLM ([src/kb/retrieval/router.py](src/kb/retrieval/router.py), `KB_ROUTER_MODEL`, default `gpt-4.1-mini`) classifies the question and plans the search for its type. Every search in a plan is the full pipeline above (embed, vector + keyword + graph, RRF, rerank against that search's own question, thresholds).

| Type | Example | Search |
|---|---|---|
| `normal` | "Which standard is the forensic lab accredited to?" | one search |
| `multi_intent` | "How many staff does CANU have, and how big is the forensic lab?" | the question and each part in parallel, best results interleaved |
| `comparison` | "How does leave approval work at MoHA versus the Prison Service?" | the question and one search per side, interleaved |
| `multi_hop` | "What is the name of the official who signs off on major fire reports?" | step by step: step 1 is searched, an LLM reads its results and writes step 2 with the answer filled in ("...the Minister of Home Affairs"), then step 2 is searched; the question itself is searched alongside |
| `conditional` | "I'm a Venezuelan student who came in through Lethem, do I pay to extend my stay?" | the question and the rule restated plainly, interleaved |
| `list` | "Which agencies have asked for an HR system?" | one wider search (`KB_LIST_TOP_K`, 10 results), the best result of each process first |
| `process` | "Walk me through how a prison buys goods." | one search, then the matched process's chunks (same `service`) in document order, up to `KB_PROCESS_MAX_CHUNKS` (8) |

Multi-part answers keep up to `KB_MAX_MERGED_RESULTS` (10) passages; at most `KB_ROUTER_MAX_SUBQUESTIONS` (3) parts or steps. The response carries `query_type`, `sub_questions`, and each result's `sub_question`. Questions under `KB_ROUTER_MIN_WORDS` (5) words skip the LLM and are `normal`; a failed or unclear classification is `normal` too, and every plan also searches the original question, so a wrong label costs time, not results. Per request, `"router": false` makes it one plain search.

Graph search also walks facts up to `KB_GRAPH_HOPS` (2) steps from each entity the question names and returns the facts on the path, so the answer can chain them (role -PERFORMED_BY- service -GOVERNED_BY-> law) and cite each link.

[eval/questions_types.jsonl](eval/questions_types.jsonl) labels questions by `type`; `kb eval` then reports the metrics per type, and for the router how often its type matched the label (`type_accuracy`). `kb eval --compare` adds a `router` row. The router adds one small LLM call per question, plus one search per part (more rerank calls: mind a trial Cohere key's rate limit).

## Knowledge drift

Documents describe the rules on the day they were written; when the real rules change, the knowledge base drifts out of date without any error. Four pieces handle that:

| Job | How |
|---|---|
| **Detect** | Every version records its `source`: the file's full path for `kb ingest`, or `--source-url` / form field `source_url` for a web address. `kb refresh` (or `POST /documents/refresh`) re-reads each current document's source. URLs use `ETag` / `Last-Modified`, so unchanged files aren't downloaded again. |
| **Update** | Changed content is ingested as the next version of the same `doc_key`: re-chunked, re-embedded, old version superseded and kept as history, user metadata carried over. Unchanged content only updates `last_checked_at`. `--dry-run` reports changes without ingesting. |
| **Expire** | `--valid-until` keeps a version out of search after that date (unchanged). |
| **Warn** | `kb stale` (or `GET /documents/stale`) lists current documents whose `review_by` date has passed, that are older than `KB_MAX_DOCUMENT_AGE_DAYS` with no review date, that have expired, or whose source has disappeared (`source_status = missing`) or can't be read (`error`). Search adds a `warnings` entry for every cited document in that state. |

A vanished source is only flagged, never deleted automatically: the document stays searchable until someone replaces, expires (`--valid-until`) or deletes it.

Documents ingested before this feature have no source. Running `kb ingest <their folder>` once records it: unchanged files come back as `duplicate` but now have a `source`.

### Running it automatically

[scripts/drift-check.ps1](scripts/drift-check.ps1) runs `kb ingest <inbox>` (optional: picks up files dropped into a folder), `kb refresh` and `kb stale`, and appends the output to `logs\drift-YYYY-MM-DD.log`. It exits with code 1 when something needs a person (a missing or unreadable source, a stale document). Schedule it daily with Task Scheduler:

```powershell
$action  = New-ScheduledTaskAction -Execute "powershell.exe" `
  -Argument "-NoProfile -ExecutionPolicy Bypass -File `"$PWD\scripts\drift-check.ps1`" -Inbox C:\askgov\inbox"
$trigger = New-ScheduledTaskTrigger -Daily -At 6am
Register-ScheduledTask -TaskName "AskGov drift check" -Action $action -Trigger $trigger
```

`kb refresh` re-embeds the whole document when anything in it changes, so each update costs one embedding run for that document.

## Evaluation

Two evaluations read the same file, [eval/questions.jsonl](eval/questions.jsonl). Each line holds a question, an `expected` label (filename plus a phrase from the right chunk) and a `reference` answer in plain text. Neither uses chunk IDs, so the labels still work after re-ingesting or re-chunking.

```powershell
kb eval eval/questions.jsonl --compare --delay 6.5     # exact label matching: hit@1, hit@k, MRR, refusals (cheap)
pip install -e ".[eval]"
kb deepeval eval/questions.jsonl --delay 6.5 --out eval/deepeval.json   # LLM judge (DeepEval), costs judge calls
```

`kb deepeval` generates an answer for each question from the retrieved chunks (`KB_GENERATION_MODEL`, default `gpt-4o-mini`). A judge model (`--judge-model`, default `gpt-4.1`; `gpt-4o-mini` is cheaper but misreads more sources) then scores both the chunks and the answer:

| Group | Metric | Checks |
|---|---|---|
| retrieval | contextual_precision | relevant chunks rank above irrelevant ones |
| retrieval | contextual_recall | the chunks contain everything the reference needs |
| retrieval | contextual_relevancy | how much of the retrieved text is on topic |
| answer | **correctness** | the answer agrees with the `reference` (G-Eval) |
| answer | **faithfulness** | every claim in the answer is supported by the chunks |
| answer | **answer_relevancy** | the answer addresses the question |

`--metrics retrieval|answer|all` picks the groups; the default is `all`. Each score comes with the judge's reason, and the report also stores each generated answer. To try one answer by hand: `kb ask "price of a birth certificate copy"`. Questions without a `reference` (the off-topic ones) are skipped, because `kb eval` checks refusals. Use `--limit 5` or `--only id1,id2` for a quick check. `--delay 6.5` keeps a Cohere trial key under its 10 calls/minute limit.
